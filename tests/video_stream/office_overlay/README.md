# 办公小字 JPEG 局部补帧

基准是 `379d180a5248ac1e80fccea0148d214d2bdae494`。运行器用 `git archive` 提取该提交到临时目录，并从归档运行中继、Python 发送代理、Mac 本地服务和产品页面。WKWebView 离屏运行，H.264 由 WebCodecs 解码，Vision 从实际画布按窗口尺寸与 DPR 取样。归档使用同一提交的中文姓名、日期、金额生成器，以及逐格完全匹配的 OCR 规则。执行时只连接 127.0.0.1。每轮先用错误的证书指纹确认连接被拒绝，再用正确指纹完成 TLS 握手和真实授权。

## 复跑

需要带 Vision 中文 OCR 和 Hiragino Sans GB 的 macOS、Xcode Command Line Tools，以及已缓存的 Python 3.12 与测试依赖。命令从工作树根目录运行。

```sh
uv run --offline --no-project --python 3.12 \
  --with-requirements tests/video_stream/requirements.txt \
  python tests/video_stream/office_overlay/run.py \
  --rates 1 1.6 --seeds 0 17 93 --modes avc jpeg \
  --output /tmp/lanpilot-office-overlay.json.gz
node tests/video_stream/office_overlay/test_overlay.js
```

如果有现成环境，可用它的 Python 直接运行 `run.py`。每轮约 35–45 秒，数据在每轮结束后原子更新。程序异常保存在压缩 JSON 的 `failures`，读数和 guard 失败保存在逐轮记录。可用 `--modes jpeg-diverse` 单独复跑降权周期纹理的探索方案。该方案在窗口内保留因批次容量未发送的补丁，JPEG 质量为 62。原细节排序方案使用质量 75。探索对照参数为 `--rates 1 1.6 --seeds 0 991 --modes jpeg-diverse`。

## 设计与口径

- 两组共用 1280×720、20 fps、750 kbps 和 100 kbit VBV 的 H.264 合成发送逻辑。中继到 Mac 的 TCP 代理限速为 1 或 1.6 Mbps，双向传播各加 300 ms。上行发送代理与中继回环直连。每轮从产品打开会话起观测 25 秒。
- 按全帧 RGB 哈希判断像素是否稳定。在连续 6 个采样间隔后，对整个桌面按 384×216 固定网格计算灰度高频能量并排序。一个静止期最多 96 KiB Base64 JPEG 负载。种子 0 保留原位置，其他种子确定性平移整个场景。OCR 的裁剪位置、字段内容和评分真值没有传给选择器。
- 补丁使用中继测试注入点和现有 H.264 TLS 下行，同样经过批次大小限制和共享限速。合成源的 RGB 像素在测试进程内交给补丁生成器，原型没有测 Windows 端采集、JPEG 上行或 Windows CPU 成本。只观测本机回环上的下行。
- 补丁需与当前显示的基础帧序号、几何、原始尺寸、会话和源图版本一致。JPEG 异步解码前后都检查。后续每张 H.264 基础帧只有带相同像素版本和几何时才可继续叠加。收到其他版本先恢复原 H.264 像素，超过基础帧 2.5 秒则清除覆盖。叠加只重绘画布，基础帧及输入时间戳仍由产品维护，1.5 秒的输入新鲜度窗口照常检查。
- 起播和停滚分别从发起连接及源端真正停滚计时。取第一段连续 5 秒维持 18/18 的起点，确认这个结果还需再观察 5 秒。重滚同时测源端恢复移动到清除旧补丁、源端恢复移动到第一张移动画面，以及移动画面有没有补丁。字节按中继写出的 JSON 媒体记录所计，包含 Base64，不含 TLS/TCP 和控制消息。输入用真实产品队列及合成 mailbox 测移动事件确认，并在帧已过期时提交探针检查它无法入队。

## 采用门槛

在 1 和 1.6 Mbps、600 ms RTT 的回环矩阵中，换用未参与排序设计的版面也要连续 5 秒识对 18 个字段。以本试验只有约 8 秒的停滚窗口为准，第一段全对最迟应在停滚后 3 秒开始。建议将配对的 25 秒下行媒体字节增量控制在 20% 内，输入确认 P95 增量控制在 150 ms 内，并逐轮核对首张移动画面和输入保护。补帧需要明确的字节预算，并在批次即将满载时优先给 H.264 保留容量。重滚新画面不得出现旧图块。异步解码完成时若基础帧已换、已过期或已回退，必须丢弃补丁。输入仍应由原基础帧的年龄决定。进入产品前还需验证 Windows 实际采集、上行开销及滚轮和点击的画面反馈。

## 主对照结果

证书指纹错误在每轮都被拒绝。正确指纹的暖连接 RPC 中位数为 606–617 ms。12 轮的未编码源图检查全部为 18/18。25 秒窗口内持续使用 H.264，各轮停滚后约有 8 秒可供观察。两种方案在起播和停滚后均未出现 18/18，因此首次全对及连续全对的时间都没有观测值。下表列单次峰值。

| Mbps | 种子与位移 px | 起播最佳 H.264 → JPEG | 停滚最佳 H.264 → JPEG | 媒体 KiB H.264 → JPEG | 输入回执 P95 ms H.264 → JPEG |
| --- | --- | ---: | ---: | ---: | ---: |
| 1 | 0 · (0, 0) | 0 → 1 | 2 → 3 | 304.5 → 579.4 | 1,300 → 1,549 |
| 1 | 17 · (558, 65) | 1 → 6 | 6 → 10 | 347.3 → 453.7 | 1,392 → 1,748 |
| 1 | 93 · (530, 129) | 1 → 16 | 11 → 10 | 370.1 → 454.1 | 1,350 → 1,400 |
| 1.6 | 0 · (0, 0) | 0 → 1 | 0 → 2 | 296.8 → 553.3 | 1,300 → 1,450 |
| 1.6 | 17 · (558, 65) | 12 → 10 | 2 → 13 | 352.4 → 530.7 | 1,400 → 1,499 |
| 1.6 | 93 · (530, 129) | 2 → 17 | 4 → 2 | 400.4 → 515.6 | 1,354 → 1,369 |

6 组配对的媒体字节增量为 23%–90%。未平移时，细节选择器主要把字节花在反复出现的办公文字，目标小字所在的左上图块没有入选。平移改善部分覆盖，但原始细节能量仍会优先给其他区域，另有发不进当前批次的候选图块被当前实现跳过。输入事件全部收到合成邮箱回执和 Viewer 确认（H.264 84/84，补帧 85/85）。补帧输入回执 P95 较配对基线上升 15–356 ms。

补帧路径实际叠加了 38 块。6 轮的新移动画面均未出现旧 JPEG 图块。4 轮在源端重滚时仍有旧覆盖，从源端开始移动到清除耗时 400–1,138 ms，相应轮次均在首张新移动帧绘制前清除。其余 2 轮在重滚前已因超时清除。恢复 H.264 的像素逐字节一致。所有叠加前后的输入帧对象与输入时间戳一致。WKWebView 拒绝了几何、序号、版本、范围和到期不匹配的本地探针，补丁仍可见时也有过期输入探针被产品挡住。Node 回归另外复现了等待解码时换帧、收到新源版本、到期以及回退。

主矩阵使用原型的第一版有效报文路径。其后增加了源图缓存边界、报文形状检查，以及回退和关闭时对待解码图块的清理。更早的原位小样 `smoke.json.gz` 也保留，停滚和起播的峰值均为 0/18。

## 降低重复纹理权重的补充试验

沿纵向在 12–47 像素间搜索相似的高频图案，对重复纹理降权。这个方案同时把 JPEG 质量从 75 改为 62，并保留当前批次装不下的候选，结果反映三项改动的合并效果。种子 991 的位移是 (174, 70)，用于探索新位置，没有同种子的纯 H.264 配对轮次。

| Mbps | 种子 | 起播首次 18/18 ms | 停滚首次 18/18 ms | 连续 5 秒全对的起点，起播 / 停滚 ms | 起播 / 停滚最佳 | 媒体 KiB |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 0 | 3,450 | 1,221 | 3,450 / 1,221 | 18 / 18 | 511.7 |
| 1 | 991 | — | — | — / — | 9 / 17 | 495.7 |
| 1.6 | 0 | 3,733 | 2,543 | — / — | 18 / 18 | 492.2 |
| 1.6 | 991 | — | — | — / — | 10 / 9 | 440.8 |

1 Mbps 原位样本在停滚 6.221 秒时确认了连续 5 秒全对。1.6 Mbps 原位样本在基础帧更新间隔拉长后，覆盖触发超时，使全对未能维持。1 Mbps 移位样本的最高分漏项为金额 `14,411.86`，Vision 在补帧画布上读成 `14.411.86`。原位配对媒体字节增加约 66%–68%。4 轮共叠加 48 块，53/53 次合成指针输入得到确认。过期输入探针全被拦截，重滚后首张新移动帧及后续移动帧均无旧覆盖。所有清除均恢复原 H.264 像素。

补充试验首次运行因 NumPy `float32` 排名分数不能写入 JSON 导致媒体流拒绝，已转换为 Python `float` 后复跑完整 4 轮。原失败保存在 `diverse-failed.json.gz` 与日志中。macOS 26.7 arm64，Python 3.12.14，PyAV 16.1.0，NumPy 2.4.2，Pillow 12.1.1。

现阶段保留为测试原型。优先解决随机位置覆盖、恢复基础帧时的图块连续性和媒体预算，再按上述采用门槛验收。
